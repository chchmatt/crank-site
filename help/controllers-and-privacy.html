Controllers, the API and your privacy

The controller is the program on your computer that runs a project. This page covers how it's identified, why only one runs a project at a time, how it talks to Crank, and what never leaves your computer.

What never leaves your computer Coming soon (CB-55, CB-60, CB-63, CB-67)

No telemetry leaves your computer. Specifically, none of these is ever sent to the website, the API, an alert or any service:

  1. Logs from the controller or the runners.
  2. Memory readings, or any history of them. There are no memory charts.
  3. Claude usage figures (see Usage and schedules).
  4. Details of the computer: its name, specs, operating system user, folder paths or IP address.

What is sent: the queue's state (jobs, titles, states, notes, topics), the plain reasons shown on the page, the heartbeat time, and your commands. Your code stays in your repository.

Why: "Details of the PC should never be exposed", and "no logs from the runner or the controller are sent anywhere". Memory charts were dropped for the same reason: "the same leak".

Source: CB-55, CB-60, CB-63, CB-67; agreed 25 Nov 2026.

How a controller is known Coming soon (CB-53, CB-55)

  1. By a random id and a name you choose, such as "Controller 1". Never by the computer's name.
  2. Each controller has its own key, made by the API and shown once. You can revoke it, and that controller is refused at once.

Source: CB-53, CB-55.

Limits are set on the website, kept on the computer Coming soon (CB-61, CB-63)

  1. Each controller's limits (maximum runners, free memory needed before starting a runner, memory cap per runner) are set in project settings, in a Controllers section that lists each controller by name, whether it runs the project now, and when it was last heard.
  2. The controller downloads them, keeps a copy so it works offline, and enforces them on the computer. A change is picked up within one heartbeat.
  3. Saving shows "Saved" in place; no pop-up.

Source: CB-61, CB-63.

Everything goes through the Crank API Coming soon (CB-51, CB-52, CB-53, CB-54, CB-55, CB-56)

  1. The status page and every controller talk only to api.crankbuild.com. Only the API touches Crank's storage, through its own identity, so neither your computer nor the page holds a storage key.
  2. The API checks every command against the same rules the controller uses, so a bad command is refused at the door.
  3. Only crankbuild.com and www.crankbuild.com may call it from a browser.
  4. Why: before, the controllers had "too much power", connecting straight to Azure, and anyone with the computer's files could write anything.

Source: CB-51 to CB-56.

One controller per project: the lease Coming soon (CB-45, CB-53, CB-54)

  1. Only one controller runs a project at a time. It holds the project's lease, which lasts 5 minutes and is renewed by the heartbeat every 30 seconds.
  2. A controller that starts while another holds a live lease starts no runners. The page and app say "Run by Controller 1 (last heard HH:MM)".
  3. A controller that can't renew stops its own runners before its lease runs out (about 4 minutes without contact): each finishes its current step, any still running after 3 minutes are ended, their work is saved on their branches, and nothing new starts until it holds the lease again.
  4. Every call carries the lease's number, so an old controller that comes back can't write over the new one.
  5. Why: two controllers running the same project would build the same jobs twice and fight over branches.

Source: CB-45, CB-53, CB-54.

Taking over Coming soon (CB-45, CB-55)

  1. Taking over is only ever by your button. Nothing takes over by itself. Why: a controller that's merely slow shouldn't be replaced behind your back.
  2. When the lease has expired, the page and the desktop app show "Controller 1 has gone quiet since HH:MM", with Take over and a confirm.
  3. The jobs the old controller had Building go back Queued at the front of their topics, with "Interrupted: taken over from Controller 1".
  4. If the old controller comes back and finds the lease taken, it starts nothing. It pushes any work it had saved to a separate side branch (never the job's own branch, which the new controller may be using), says so, and stays idle until you take the project back.

Source: CB-45, CB-55.

The desktop app Coming soon (CB-46, CB-48)

  1. One app for all your projects, each with its own Run switch, its own controller and its own separate logs.
  2. It's a thin client. Settings live on the website; the app shows them, and has local emergency controls (End task, End all tasks, End after, Start runners) that work offline.
  3. A tray icon: green building, grey idle, amber runners ended after their jobs, red needs you or lost contact.
  4. A window with each runner's live output, each runner's current memory use (live only: nothing stored, no charts), and a local copy of the status page that works offline.
  5. Logs stay on the computer, in a folder per project, kept 14 days. "Copy logs" zips them to a file you choose, without tokens or the page's secret link.
  6. It keeps the computer awake while a job is building; it warns below 5 GB free disk space and starts no runners below 1 GB.
  7. It checks on first run that Claude Code, git and GitHub access are ready, and starts nothing until they are.
  8. It shows a notification only when something needs you. Windows first; unsigned at first, so Windows may ask you to confirm when installing.
  9. Updates install only when no job is building.

Source: CB-46, CB-48.

The status page's link Coming soon (CB-39, CB-55)

Until sign-in arrives, your project's status page link has a secret part after the #. That part is sent only in a request header, never in an address, a log or anything others can see. Treat the link like a password: anyone with it can see and steer your queue.

Source: CB-39, CB-55.

Coming later: accounts and sign-in

Planned, not yet built:

  1. No passwords, ever. Sign in with an emailed one-time code, Google or Microsoft. GitHub later.
  2. Personal details (email, name) are stored encrypted with a key of your own. When you ask to be forgotten, that key is thrown away, so your details can never be read again. Forgetting completes within 7 days (when the last backup of the keys expires).

Source: event sourcing design, sections 9.4, 9.8, 9.9.
