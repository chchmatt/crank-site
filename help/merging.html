Merging

Merging is how finished work reaches your main code. Crank merges in two steps:

  1. Job into topic. When a job is finished and its checks pass, its work is merged into its topic's branch. The job is now Built.
  2. Topic into base. When the topic is ready and its merge rule allows, the whole topic is merged into its base branch (usually main). Every job in that merge is now Merged.

When a topic is ready to merge Coming soon (CB-72)

A topic is ready when nothing in it is Building or Needs operator, and at least one of its jobs is Built.

  1. Paused, scheduled, Queued and Waiting jobs don't hold the merge back. They join a later merge.
  2. Only the jobs that were merged are marked Merged. The topic shows as "partly merged" while it still has open jobs.
  3. After a merge, the topic carries on. Its next job starts fresh from the merged code.
  4. While a topic is merging, no new job starts in it, so nothing lands mid-merge.
  5. Why it's safe: each job is built on its own branch and only reaches the topic branch once it's finished and its checks pass. A job that hasn't started, or stopped part way, has its work only on its own branch. So the topic branch only ever holds finished work, and only finished work reaches main.
  6. Why the rule changed: before, one paused job held back everything already built in its topic.

Source: CB-72.

Tested against main, then a quick merge

  1. When a topic is ready, its own runner does the final step: brings in the latest of its base branch, runs the full checks, fixes anything that fails, and records which version of the base it was tested against. The topic shows "Testing against main".
  2. This step is a run of the topic's runner, so it obeys the topic's start window and the usage threshold like any job. Why: it uses your computer and your Claude plan, so it should fit your schedule.
  3. When the merge is due, if the base hasn't changed since that test, the merge runner merges at once, with no more tests. If the base has moved, the topic's runner tests again first.
  4. Keep up to date while waiting (per topic, off by default): when on, the topic re-tests each time its base changes while it waits. Why off by default: it uses your computer's CPU each time main changes. When off, it's tested again only when the merge is due.

Source: CB-73.

Testing and merging on request Coming soon

Agreed 25 Nov 2026 (Matthew). Not queued yet, so these are Coming soon.

Test after current job

  1. A button on each topic: Test after current job. When the topic's current job finishes, its runner runs the full checks on the topic branch, fixes anything that fails, and stops there. Nothing is merged into the base.
  2. By default it first brings in the latest of the topic's base branch (for example main), so you learn whether the topic still works with everyone else's merged work. An option lets you test the topic as it is, without pulling.
  3. Other jobs in the topic wait while it runs, then carry on.
  4. Why: a topic can collect many jobs, each with only its own light checks, before anything runs the full test suite. This lets you check the whole topic part way, without committing to a merge.

Test and merge after current job

  1. A button on each topic: Test and merge after current job. When the current job finishes, the topic's runner always brings in the latest of its base branch, runs the full checks, fixes anything that fails, and then the topic merges into its base.
  2. It overrides the topic's merge rule (Hold, Not before, After topics) for this one merge. Why: pressing it means you want this topic merged now.
  3. It always pulls the base first. Why: a merge must be tested against the base it's merging into; otherwise a merge could break the base.
  4. It still obeys the usage threshold, like every run.

A topic merges only between jobs

  1. While a topic is testing or merging, the other jobs in that topic wait. A job already building finishes first; nothing new starts in the topic until the merge is done.
  2. Why not merge from a copy while the topic keeps building? If the tests fail and need fixes, those fixes would have to land in two places: in the copy being merged, and in the topic branch where new work had already moved on. Waiting keeps one branch and one place to fix.
  3. Other topics carry on as normal.

Automatic full tests

  1. A per-topic setting, off by default: run a full test (as Test after current job, pulling the base by default) every N jobs, every N hours, or both, whichever comes first.
  2. It runs between jobs, like the buttons, and obeys the topic's start window and the usage threshold.
  3. Why both: five small jobs might take five minutes, so "every 5 jobs" would test too often; a time gap fits that case better. Long jobs suit a job count.
  4. Why off by default: full tests use your computer and your Claude plan.

When a merge fails Coming soon (CB-72)

  1. The jobs stay Built. The topic gets a note, for example "merge blocked, fix job CB-29".
  2. Crank adds a fix job to the topic ("Fix at the merge to main: …"), which finds the cause and makes the smallest fix. It's a normal job. The next merge waits until it's Built.
  3. The note goes when the merge succeeds.

Source: CB-31, CB-72.

Base branches other than main Coming soon (CB-75, CB-76, CB-78)

Some work stays on its own long-lived branch for a while, for example version-2.

  1. Each topic has a base branch, main by default. The topic is started from it, tested against it, and merged back into it. In settings: "This topic is branched from, tested against and merged back into this branch."
  2. A new base branch is made from main once, the first time a topic uses it. After that, main is never merged into it automatically. Why: a fix on main should be done properly in the feature branch when it's wanted, not pulled in by surprise.
  3. A topic's base can't be changed once its branch holds built work.
  4. All the merge rules above apply per base. A job is Merged when its topic reaches the topic's own base, shown as "Merged into version-2" when that isn't main.
  5. Merging version-2 into main isn't automatic. For now, do it as a job in a topic whose base is main, or by hand.

Source: CB-75, CB-76, CB-78.

Merge lanes Coming soon (CB-75, CB-76)

  1. There's one merge lane per base branch, so a merge into version-2 never holds up a merge into main. Each lane merges one topic at a time.
  2. The lane for main starts at once.
  3. For each other base, you choose: "Starts immediately", or "Uses the runner pool" (waits for a free runner slot and counts toward maximum runners). The pool is the default. Why: it's your computer; extra lanes shouldn't add load unless you say so.
  4. The merge runner card shows each busy lane, for example "merging api into version-2" or "waiting for a runner slot".

Source: CB-75, CB-76.
